01 / Overview

What Is Titan KV?

Titan KV is a ground-up implementation of a Redis-compatible key-value store written entirely in safe Rust. It is not a wrapper, a binding, or a port — it is an original engine built to understand and replicate the core mechanics that make Redis one of the most battle-tested data stores in existence.

It speaks the Redis wire protocol on port 6379, which means any Redis client — redis-cli, nc, your application's existing Redis library — can connect without modification.

The engine now runs a 64-shard architecture — each key is hash-routed to one of 64 independent RwLock shards, allowing up to 64 concurrent writers with zero contention. New queue primitives (RPOPLPUSH, LREM) power reliable, crash-safe job processing patterns.

02 / Internals

Architecture

Each client connection is an independent Tokio task. A ShardedDb of 64 independent RwLock shards guards in-memory state. Three background tasks manage expiration, AOF logging, and periodic compaction — each aware of the full shard array.

03 / Components

Core Components

Seven modules, each with a single clear responsibility. Exploring one file is enough to understand any given behavior in full.

🦀
engine.rs
The Heart — ShardedDb
The database is a ShardedDb: an Arc-wrapped array of 64 independent RwLock<HashMap<String, Entry>> shards. Each key hashes to exactly one shard (hash(key) & 0x3F). write_multi_shards() handles cross-shard ops with ordered lock acquisition to prevent deadlock.
🌐
server.rs
The Listener
A Tokio TcpListener accepts connections in a tight loop. Each accepted connection is handed off to tokio::spawn, giving every client its own lightweight async task. Manages RESP input, command dispatch against the sharded DB, AOF writes, and response serialization for all 21 commands.
⟨/⟩
protocol.rs
The Parser
A complete RESP-compatible reader and parser. read_resp() handles both raw text and RESP array framing. parse_command() returns a strongly-typed Command enum covering all scalar, list, hash, pubsub, and queue operations including RPOPLPUSH and LREM.
📡
pubsub.rs
Event Broker
Real-time pub/sub via Tokio broadcast channels. The registry is an Arc<RwLock<HashMap<String, broadcast::Sender<String>>>>. Subscribers pause regular command parsing and block on tokio::select! awaiting either a broadcast message or an UNSUBSCRIBE from the client.
📋
logger.rs
The Monitor
Macro-driven logging using chrono and colored. Exports log_info!, log_warn!, log_error!, log_debug!, log_success!. Each entry is timestamped, color-coded by severity, and tagged with a context string.
🔧
main.rs
The Orchestrator
Startup pipeline: (1) AOF replay — re-executes commands routing each key to the correct shard. (2) Spawn expiration sweeper (10s tick, iterates all 64 shards). (3) Spawn AOF compaction task (60s tick, scans all 64 shards). (4) Hand off to server::run().
🧵
thread_pool.rs
Historical Artifact
A fully hand-rolled OS thread pool using std::sync::mpsc and Arc<Mutex<Receiver>>. The Drop impl drains the channel and joins all threads for graceful shutdown. Retained as a foundational artifact — the concurrency model was understood before Tokio abstracted it away.
04 / Engine

64-Shard Engine

The engine was refactored from a single global RwLock to a ShardedDb — an array of 64 independent shards. Every key maps deterministically to exactly one shard via a 64-bit hash. Hover a shard below to see its index.

⬡
Hash Routing
shard = hash(key) & 0x3F
Every operation calls calculate_shard_index(key) using DefaultHasher. The 64-bit hash is masked to 6 bits — giving 64 deterministic, evenly-distributed slots. Same key always hits same shard.
🔀
Cross-Shard Safety
write_multi_shards()
RPOPLPUSH may span two shards. write_multi_shards() always acquires the lower-index shard first — making deadlock structurally impossible. If both keys hash to the same shard, a single guard is returned.
⚡
Parallel Writes
64 concurrent writers
A writer on shard 17 does not block a writer on shard 42. Under a workload with uniform key distribution, write throughput scales linearly until hitting I/O or CPU limits — not the lock.
64 Shards — each is an independent RwLock<HashMap<String, Entry>>
shard routing example
# Each key hashes to a specific shard — independently lockable
hash("queue:jobs") & 0x3F → shard 17
hash("queue:done") & 0x3F → shard 42
hash("session:abc") & 0x3F → shard 5

# RPOPLPUSH — cross-shard, always deadlock-free
$ RPOPLPUSH queue:jobs queue:done
1. acquire write guard on shard 17 (lower index)
2. acquire write guard on shard 42 (higher index)
3. pop tail of queue:jobs, push head of queue:done
4. release both guards atomically

06 / Durability

Persistence: The AOF Model

Titan KV uses an Append-Only File for persistence — the same model Redis uses in appendonly yes mode. Compaction now scans all 64 shards to build the minimal log.

✍️
On Every Write
Every mutating command — including RPOPLPUSH and LREM — is serialized to database.aof before the response is sent. If the process dies at any moment, the on-disk log is authoritative.
▶️
On Startup (Replay)
The AOF is replayed top-to-bottom. Each command is re-executed against the sharded engine — routing every key to its correct shard. In-memory state is deterministically reconstructed in milliseconds.
♻️
Every 60s (Compaction)
The compaction task iterates all 64 shards, serializes only the current live state to database.temp.aof, and atomically renames it over the live log. A crash mid-compaction never corrupts the live file.

07 / Lifecycle

Expiration: Two Strategies in Tandem

Titan KV implements the same dual-expiry pattern Redis uses. Neither strategy alone is sufficient; together they guarantee no key outlives its TTL — even across 64 shards.

Lazy Expiration ON READ
When GET is called, the handler checks expires_at against SystemTime::now(). If stale: key deleted from its shard, DEL appended to AOF, $-1 returned. Zero overhead for non-expiring keys.
Active Expiration BACKGROUND
A sweeper wakes every 10 seconds, iterates across all 64 shards in sequence, collects expired keys per shard, removes them in batch, and flushes DEL entries to the AOF. Prevents unread keys from accumulating in memory.
expiration walkthrough
$ redis-cli SETEX session:abc 30 "user_data"
OK

# t+0s — key is fresh
$ redis-cli GET session:abc
"user_data"

# t+31s — lazy expiry fires on GET
$ redis-cli GET session:abc
(nil)

# alternatively — sweeper at t+10s tick evicts across all 64 shards
[DBUG] [Sweeper] Active Expiration Swept key: session:abc

10 / Deployment

Docker

Titan KV ships with a multi-stage Dockerfile. The build stage compiles the Rust binary; the runtime stage is a minimal Debian image containing only the compiled binary.

Multi-Stage Build
Stage 1 (rust:1.81-slim-bookworm) compiles the binary with cargo build --release. Stage 2 (debian:bookworm-slim) copies only the resulting binary — no Rust toolchain, no source code, no intermediate artifacts. The final image is lean and production-ready.
docker
# Build
$ docker build -t titan_kv .

# Run — maps port 6379
$ docker run -p 6379:6379 titan_kv
[ OK ] [Server] Titan KV natively deployed and listening on 127.0.0.1:6379

# Run with persistent AOF volume
$ docker run -p 6379:6379 -v $(pwd)/data:/app titan_kv

# Verify from host
$ redis-cli -p 6379 PING
PONG
11 / Concurrency

Concurrency Model

Every client connection is an independent Tokio task. The shared state is a ShardedDb — an array of 64 independent RwLock shards. Key distribution across shards is automatic and deterministic.

∞
Concurrent Readers / Shard
GET, EXISTS, LRANGE, HGET, HGETALL acquire a shard read guard. Reads on the same shard don't block each other. Reads on different shards are completely independent.
64
Max Concurrent Writers
SET, DEL, INCR, LPUSH, RPUSH, etc. lock exactly one shard. Writes to different shards proceed in parallel with zero contention — up to 64 simultaneous writers.
⬡
Cross-Shard Atomicity
RPOPLPUSH may span two shards. write_multi_shards() acquires both write guards in ascending index order (lower index first), making deadlock structurally impossible — not just unlikely.

Under a workload with a uniform key distribution, write throughput scales linearly until hitting I/O or CPU limits — not the lock. The single global lock bottleneck is gone. The next tuning target is AOF fsync latency.

12 / Safety

Titan KV contains zero unsafe blocks. The Rust compiler's ownership model provides compile-time guarantees that a GC language cannot.
