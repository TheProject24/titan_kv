01 / Overview

What Is Titan KV?

Titan KV is a ground-up implementation of a Redis-compatible key-value store written entirely in safe Rust. It is not a wrapper, a binding, or a port — it is an original engine built to understand and replicate the core mechanics that make Redis one of the most battle-tested data stores in existence.

It speaks the Redis wire protocol on port 6379, which means any Redis client — redis-cli, nc, your application's existing Redis library — can connect without modification.

The goal is not to beat Redis. The goal is to understand what it takes to build something like it: the concurrency model, the durability guarantees, the expiration mechanics, the persistence format. Every line of Titan KV exists as a deliberate engineering decision.

02 / Internals

Architecture

Each client connection is an independent Tokio task. A single Arc<RwLock<...>> guards in-memory state. Three background tasks manage expiration, AOF logging, and periodic compaction.

03 / Components

Core Components

Seven modules, each with a single clear responsibility. Exploring one file is enough to understand any given behavior in full.

🦀
engine.rs
The Heart
The database is a single type: Arc<RwLock<HashMap<String, Entry>>>. Arc enables shared ownership across async tasks. RwLock allows unlimited concurrent readers while serializing writes. Each Entry holds a DataType variant and an expires_at: Option<SystemTime>.
🌐
server.rs
The Listener
A Tokio TcpListener accepts connections in a tight loop. Each accepted connection is handed off to tokio::spawn, giving every client its own lightweight async task. Manages RESP input, command dispatch, AOF writes, and response serialization for all 19 commands.
⟨/⟩
protocol.rs
The Parser
A complete RESP-compatible reader and parser. read_resp() handles both raw text and RESP array framing. parse_command() tokenizes the stream and returns a strongly-typed Command enum covering all scalar, list, hash, and pubsub operations.
📡
pubsub.rs
Event Broker
Real-time pub/sub via Tokio broadcast channels. The registry is an Arc<RwLock<HashMap<String, broadcast::Sender<String>>>>. Subscribers pause regular command parsing and block on tokio::select! awaiting either a broadcast message or an UNSUBSCRIBE from the client.
📋
logger.rs
The Monitor
Macro-driven logging using chrono and colored. Exports log_info!, log_warn!, log_error!, log_debug!, log_success!. Each entry is timestamped, color-coded by severity, and tagged with a context string.
🔧
main.rs
The Orchestrator
Startup pipeline: (1) AOF replay — line-by-line command re-execution to restore in-memory state. (2) Spawn active expiration sweeper (10s tick). (3) Spawn AOF compaction task (60s tick). (4) Hand off to server::run().
🧵
thread_pool.rs
Historical Artifact
A fully hand-rolled OS thread pool using std::sync::mpsc and Arc<Mutex<Receiver>>. The Drop impl drains the channel and joins all threads for graceful shutdown. Retained as a foundational artifact — the concurrency model was understood before Tokio abstracted it away.

05 / Durability

Persistence: The AOF Model

Titan KV uses an Append-Only File for persistence — the same model Redis uses in appendonly yes mode.

✍️
On Every Write
Every mutating command is serialized to database.aof before the response is sent. If the process dies at any moment, the on-disk log is authoritative. No data is lost that was acknowledged.
▶️
On Startup (Replay)
The AOF is replayed top-to-bottom. The in-memory state is deterministically reconstructed from the command log. No binary snapshot to corrupt, no partial-write ambiguity. The database is live in milliseconds.
♻️
Every 60s (Compaction)
The compaction task serializes current live state to database.temp.aof and atomically renames it over the live log. A crash mid-compaction never corrupts the live file. Redundant history collapses: 1000 SETs on the same key become one.

06 / Lifecycle

Expiration: Two Strategies in Tandem

Titan KV implements the same dual-expiry pattern Redis uses. Neither strategy alone is sufficient; together they guarantee no key outlives its TTL.

Lazy Expiration ON READ
When GET is called, the handler checks expires_at against SystemTime::now(). If stale: key deleted, DEL appended to AOF, $-1 returned. Zero overhead for non-expiring keys; no background task required for this path.
Active Expiration BACKGROUND
A sweeper wakes every 10 seconds, acquires a write lock, collects all expired keys, removes them in batch, and flushes DEL entries to the AOF. Prevents unread keys from living forever in memory, bounding worst-case memory usage.
expiration walkthrough
$ redis-cli SETEX session:abc 30 "user_data"
OK

# t+0s — key is fresh
$ redis-cli GET session:abc
"user_data"

08 / Deployment

Docker

Titan KV ships with a multi-stage Dockerfile. The build stage compiles the Rust binary; the runtime stage is a minimal Debian image containing only the compiled binary.

Multi-Stage Build
Stage 1 (rust:1.81-slim-bookworm) compiles the binary with cargo build --release. Stage 2 (debian:bookworm-slim) copies only the resulting binary — no Rust toolchain, no source code, no intermediate artifacts. The final image is lean and production-ready.
docker
# Build
$ docker build -t titan_kv .

# Run — maps port 6379
$ docker run -p 6379:6379 titan_kv
[ OK ] [Server] Titan KV natively deployed and listening on 127.0.0.1:6379

# Run with persistent AOF volume
$ docker run -p 6379:6379 -v $(pwd)/data:/app titan_kv

# Verify from host
$ redis-cli -p 6379 PING
PONG
09 / Concurrency

Concurrency Model

Every client connection is an independent Tokio task. The shared state is a single Arc<RwLock<...>> — no per-shard locks, no lock-free tricks yet.

👁
N Concurrent Readers
GET, EXISTS, HGET, HGETALL, LRANGE acquire a read guard that does not block other reads. Unlimited concurrent read throughput under read-heavy workloads.
✏️
1 Exclusive Writer
SET, DEL, INCR, SETEX, LPUSH, RPUSH, LPOP, RPOP, LTRIM, HSET acquire a write guard that waits for all readers to finish, then serializes.

This is correct, safe, and sufficient. It is also the natural starting point for future optimization: the bottleneck under high write contention is the single global lock — which is exactly what sharded hashmaps and lock-free structures address.

10 / Safety

Memory Safety

Titan KV contains zero unsafe blocks. The Rust compiler's ownership model provides compile-time guarantees that a GC language cannot.
